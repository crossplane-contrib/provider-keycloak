# Assessment: consolidating all API groups into a single `keycloak.crossplane.io` group

Tracking issue: *Evaluation of api group consolidation* —
`crossplane-contrib/provider-keycloak#658`.

> "Api groups are growing and add complexity for no benefits. I want to evaluate
> if it is a possibility to move everything into a single
> `keycloak.crossplane.io` api group and what the implications of that are. This
> would be a breaking change that we usually try to avoid. That requires
> conversion hooks so it's something that needs to be evaluated with care."

This document is a **research / assessment**. It does **not** change any
generated types, CRDs, or configuration. Its purpose is to give the maintainers
an accurate picture of *what would have to change*, *what breaks*, *what cannot
be solved with conversion hooks*, and a concrete recommendation.

---

## 1. TL;DR / recommendation

Consolidating every managed resource into a single `keycloak.crossplane.io`
(and `keycloak.m.crossplane.io`) API group is **technically feasible with a
one-line-per-group config change**, but it is **not free** and it is **not a
problem that CRD conversion webhooks can solve**:

1. **Kind collisions are a hard blocker.** At least **8 sets of Kinds** are
   currently distinguished *only* by their API group. Collapsing the groups
   forces those Kinds to be renamed, which is a *second* breaking change layered
   on top of the group rename (see § 4).
2. **Conversion webhooks do not help here.** Crossplane/upjet CRD conversion
   only converts *between versions of the same group+kind*
   (`v1alpha1 → v1beta1`). It cannot convert `user.keycloak.crossplane.io/Roles`
   into `keycloak.crossplane.io/UserRoles`. A group (or kind) change is a
   *different CRD*, so existing CRs cannot be auto-migrated in place (see § 5).
3. **The blast radius is large but mechanical:** ~185 CRD files, 81 Kinds, 16
   short groups × 2 scopes, plus ~205 example manifests and 18 resource doc
   pages that hard-code the group in `apiVersion:` (see § 6).

**Recommendation:** do **not** pursue a full "everything in one group" collapse
in a single release. The complexity it removes (16 Go packages) is small
relative to the churn and the permanent Kind renames it forces on users. If the
goal is only to *reduce group sprawl*, prefer **Option C — targeted
consolidation** of the few genuinely redundant groups (`openidclient` +
`samlclient` → `client`, `oidc` + `saml` where they overlap) done as an
additive, opt-in migration alongside the existing groups, rather than a
big-bang rename. See § 7.

---

## 2. Current state

The provider is generated by upjet. Every managed resource carries a
`ShortGroup`, and the CRD's API group is composed at generation time as:

```
group = ShortGroup + "." + RootGroup          // when ShortGroup != ""
group = RootGroup                             // when ShortGroup == ""
```

(see upjet `pkg/pipeline/run.go`, the `resourcesGroups` loop). There are two
root groups because of the Crossplane v2 namespaced-resources work:

| Scope                | RootGroup                    | Set up in            |
|----------------------|------------------------------|----------------------|
| Cluster (legacy v1)  | `keycloak.crossplane.io`     | `config/provider.go` `GetProvider` |
| Namespaced (v2)      | `keycloak.m.crossplane.io`   | `config/provider.go` `GetProviderNamespaced` |

Today there are **16 short groups** (each emitted under *both* root groups):

```
authenticationflow  client      defaults   group     identityprovider  ldap
oidc                openidclient openidgroup organization realm          role
saml                samlclient  user       workflow
```

That yields roughly:

* **81** distinct Kinds (namespaced set),
* **185** generated CRD YAML files under `package/crds/` (93 `*.m.crossplane.io`
  + 92 `*.crossplane.io`),
* **16** hand-authored Go config packages under `config/<group>/`,
* **16** generated API packages under `apis/{cluster,namespaced}/<group>/`.

Consolidation would mean setting `ShortGroup = ""` (or a single shared value)
for every resource, so the composed group becomes exactly the root group.

---

## 3. How a consolidation would actually be implemented

Mechanically the change is small and lives entirely in `config/`:

* Every `r.ShortGroup = "<x>"` assignment in `config/<group>/config.go` would be
  removed or set to `""`. There are ~138 `ShortGroup`/reference assignments
  spread across the config packages.
* `make generate` would then regenerate `apis/` and `package/crds/` with the
  single group.

**Good news — cross-resource references survive automatically.** References are
wired by **Terraform resource name**, not by API group, e.g.:

```go
r.References["realm_id"] = ujconfig.Reference{ TerraformName: "keycloak_realm" }
```

Because `TerraformName` is group-agnostic, `realmIdRef`, `clientIdRef`,
`roleIdRef`, etc. keep resolving after a group change with **no config edits**.
That removes what would otherwise be the largest source of churn.

**Bad news — nothing else about the change is "small":** see § 4 and § 5.

---

## 4. Hard blocker: Kind collisions

Within a single API group, every Kind must be unique. Several Kinds are
currently identical and are disambiguated *only* by their group. Collapsing the
groups makes them collide, so they must be **renamed** — a breaking change on
top of the group change, and one that even a conversion webhook cannot hide.

Collisions found in the current tree (`_Kind = "..."`):

| Colliding Kind        | Groups it currently lives in                          |
|-----------------------|-------------------------------------------------------|
| `Roles`               | `defaults`, `group`, `user`                           |
| `Client`              | `openidclient`, `samlclient`                          |
| `ClientScope`         | `openidclient`, `samlclient`                          |
| `ClientDefaultScopes` | `openidclient`, `samlclient`                          |
| `IdentityProvider`    | `oidc`, `saml`                                         |
| `RoleMapper`          | `client`, `ldap`                                      |
| `Permissions`         | `group`, `user`                                       |
| `UserFederation`      | `ldap`, `user`                                         |

Each collision forces a decision that leaks into user-facing YAML, e.g.
`user.keycloak.crossplane.io/Roles` and `group.keycloak.crossplane.io/Roles`
would have to become something like `keycloak.crossplane.io/UserRoles` and
`keycloak.crossplane.io/GroupRoles`. That is *more* disruptive than the group
change itself, because it changes `kind:` in every affected manifest, not just
`apiVersion:`.

This alone is a strong argument against a naive "drop all short groups" move.

---

## 5. Why conversion webhooks do **not** solve the migration

The issue notes "that requires conversion hooks". It is important to be precise
about what Crossplane/upjet conversion can and cannot do:

* **What conversion webhooks do:** convert a CR between *versions of the same
  group and kind*, e.g. `keycloak_realm` `v1alpha1` ⇆ `v1beta1`. The provider
  already ships `Hub()`/spoke machinery for this
  (`apis/.../zz_generated.conversion_hubs.go`). The *stored* object is the same
  CRD; only the served version differs.
* **What they cannot do:** convert across a **different group** or a
  **different kind**. `user.keycloak.crossplane.io/Roles` and
  `keycloak.crossplane.io/UserRoles` are *two distinct CRDs* with distinct
  storage. There is no in-place, apiserver-level conversion between two
  different CRDs.

Consequences for existing users:

* Old CRs (`<group>.keycloak.crossplane.io/...`) remain stored under the old
  CRDs. New CRDs are empty until users re-apply manifests with the new
  `apiVersion:` (and, for the § 4 collisions, new `kind:`).
* A migration therefore has to be **data migration**, not schema conversion:
  either users re-apply their manifests, or a tool reads the old CRs and writes
  new ones (adopting the same external Keycloak object via `crossplane.io/
  external-name` + an `Observe`-only/`Import` policy so nothing is recreated in
  Keycloak).

**Precedent already in this repo:** the Crossplane v2 namespaced migration did
**not** try to convert `keycloak.crossplane.io` → `keycloak.m.crossplane.io`.
It shipped a **parallel** set of CRDs/controllers under the new root group and
let both coexist. That is the realistic template for any group consolidation:
additive parallel groups + a documented migration + eventual deprecation of the
old groups — not an in-place conversion.

## 6. Blast radius (what changes besides `config/`)

Even the mechanical parts touch a lot of files:

* **Generated API types** — 16 packages under `apis/cluster/` and
  `apis/namespaced/` regenerate; import paths (`.../apis/namespaced/user/...`)
  change, affecting `apis/*/zz_register.go` and controller wiring in
  `internal/controller/`.
* **Generated CRDs** — all ~185 files in `package/crds/` are renamed/rewritten
  (`user.keycloak.crossplane.io_roles.yaml` → `keycloak.crossplane.io_*.yaml`).
* **Examples** — ~205 manifests in `examples/` and `examples-generated/` hard-code
  the group in `apiVersion:` (32 distinct `*.keycloak[.m].crossplane.io` group
  strings appear across them). `examples-generated/` regenerates; `examples/`
  is hand-authored and must be edited by hand.
* **Docs** — 18 resource pages under `docs/content/docs/using/resources/` plus
  getting-started snippets reference the groups; `make docs-gen` must be re-run
  to refresh `docs/static/llms*.txt` so `make docs-freshness-check` passes.
* **Tooling** — `tf2crossplane` derives `apiVersion` from
  `Resource.ShortGroup + RootGroup` via `config.GetProvider(Namespaced)`, so its
  output changes automatically, but its golden/fixture tests
  (`internal/tf2crossplane`) would need updating.
* **E2E** — the manifests referenced by `cluster/test/cases.txt`
  (`dev/demos/{basic,namespaced}`) use the group in `apiVersion:` and must be
  updated in lockstep or e2e apply fails with strict-decoding errors.

None of this is conceptually hard; all of it is churn that has to land
atomically and be verified with `make generate` + `make test` + `make e2e`.

## 7. Options

### Option A — Do nothing (status quo)

Keep the 16 short groups. The "complexity" they add is mostly *organizational*
(one Go package per group); it has no runtime cost and it keeps Kinds short and
unambiguous (`user/Roles` vs `group/Roles`). Zero user disruption.

*Recommended as the default* unless a concrete pain point (not just aesthetics)
is identified.

### Option B — Full collapse into one group (big bang)

Set `ShortGroup = ""` everywhere. Requires:

* Renaming the 8 colliding Kind sets in § 4 (breaking `kind:` change).
* A parallel-group + data-migration strategy per § 5 (webhooks cannot convert).
* Rewriting all examples/docs/e2e and re-running the full generate/test/e2e loop.

High cost, permanent Kind renames, large migration burden for every user. **Not
recommended.**

### Option C — Targeted consolidation of genuinely redundant groups (recommended if we act)

Only merge groups that are conceptually the *same* domain and whose Kinds do not
collide after a small, deliberate rename, done **additively** (new group ships
alongside the old, old group deprecated over ≥1 release), following the v2
namespaced precedent. Best candidates:

* `openidclient` + `samlclient` → a single `client` group (needs Kind
  disambiguation for `Client`/`ClientScope`/`ClientDefaultScopes`, e.g.
  `OpenidClient` vs `SamlClient`).
* `oidc` + `saml` identity-provider mappers, where the split is not meaningful
  to users (needs `IdentityProvider` disambiguation).

This reduces sprawl where it actually helps, keeps each step small and testable,
and lets users migrate incrementally.

---

## 8. Suggested next steps (if the maintainers want to proceed)

1. Decide the objective: *fewer packages for maintainers* (Option A is fine) vs
   *fewer groups in user YAML* (only Option C justifies the churn).
2. If Option C: pick **one** pair of groups, implement it additively, ship an
   `Import`/`Observe`-based migration guide (adopt existing Keycloak objects via
   `crossplane.io/external-name`), and only deprecate the old group after a
   release cycle.
3. Never attempt an in-place group/kind change and call it a "conversion" — it
   is a new CRD and must be treated as a data migration.
